# The schema

The schema is a series of numbered migrations in
[`internal/db/migrations/`](../internal/db/migrations), applied in order.
`muster-server` applies them at boot. `muster-migrate` applies them on demand,
with `DATABASE_URL`.

The public tables they leave are pinned as a ledger by
`tablesThisSchemaMustHave` in `internal/db/migrate_test.go`. That test fails if
the set grows **or** shrinks.

| area | tables |
|---|---|
| tasks | `notes`, `note_comments`, `note_attachments`, `task_sessions`, `task_ref_writes` (the writes queued on a [plugin task reference](plugins.md#task-references)) |
| agents | `agents`, `chat_sessions`, `chat_messages`, `agent_retired_names`, `cc_account_marks` |
| connectors | `connectors`, `connector_grants`, `connector_standing_grants` (an owner's [shared approvals](connectors.md#shared-approvals)), `connector_audit` |
| accounts | `users`, `invites`, `api_tokens`, `audit_log`, `user_credentials` |
| mirroring | `mirror_tokens` |
| browser flows | `flow_jobs`, `flow_runner_tokens`, `flow_requests` |
| push | `push_subscriptions`, `push_preferences` |
| plugins | `plugins`, `plugin_messages`, `plugin_reply_drafts`, `plugin_threads` |
| session switcher | `pins`: the entries each user pinned (the bottom bar's **Pins** view); `recents`: the entries each user recently opened (its **Recent** view, and where home opens without a chief); `session_tags`: the [tags](mirroring.md#session-tags) each user put on a session |
| send queue | `send_queue`: messages each user queued for a mirrored Claude Code window, sent one at a time when it is idle |
| session focus | `agent_focus`: what each of a user's sessions is working on ([focus.md](focus.md)); `agent_focus_history`: every focus each session has had |
| session routing | `session_routes`: plugin messages the chief routed to a session, and how each route ended ([plugins.md](plugins.md#routing-a-message-to-a-session)); `session_prs`: the pull requests each session created and the branches it pushed, as its host's hook reported them ([plugins.md](plugins.md#a-pull-request-review-mail)); `mail_resumes`: each ended session agent mail resumed, and how it ended ([plugins.md](plugins.md#resuming-an-ended-session)) |
| attention queue | `attention_asks`: questions agents put to their owner and the answers ([attention.md](attention.md)) |
| jobs | `jobs`: one-shot machine jobs submitted over `POST /api/jobs` and their outcomes ([jobs.md](jobs.md)) |
| paired phones | `devices`: each user's paired Android phones; `device_pairing_codes`: the one-time codes that pair them; `device_challenges`: the one-time challenges their signed actions spend ([design/android.md](design/android.md#the-device-credential)) |
| suggested replies | `suggest_preferences`: each user's on/off toggle for [suggested replies](suggested-replies.md); `suggest_usage`: each user's shown / filled / sent counts, edit-distance sum and auto-pause (numbers only; no suggestion text is ever stored) |
| the chief | `chief_preferences`: each user's on/off toggle for [the chief](chief.md#turning-the-chief-on-or-off); `chief_nudges`: every [stall-nudge](chief-nudges.md) decision the chief took about one of the user's sessions, and what became of it |
| officers | `officer_llm_usage`: the [officer LLM proxy](officers.md#the-llm-proxy)'s usage, one row per officer, instance number and UTC day (requests, tokens by direction, USD booked, estimated requests; numbers only), which the daily budget is checked against; `officer_judgement_sessions`: the [judgement session cap](officers.md#the-two-pools)'s item ids per officer and UTC day |
| ask log | `asks`: every question an agent put to its owner, of every kind, with the answer, who gave it and how long it took ([asks.md](asks.md)) |
| session state | `session_episodes`: one row per stop of one of the user's sessions — a mirrored window or an agent's conversation that entered `needs_you` or `stalled` — and how it ended ([design](design/session-state.md)) |

`notes` is the task table. The name is historical. It is kept because every id in
it is a task number people cite, and renaming it would be a data migration that
buys only a word.

| migration | what it does |
|---|---|
| `0001` | The initial schema, stated as its **end state**, not as a replay of history. It is never edited. It still creates the runbook and privilege tables that `0005` drops. |
| `0002` | `agent_retired_names`: a retired agent name can never be reused. |
| `0003` | Agent kinds (existing rows become `gateway`) and the Claude Code account pool. |
| `0004` | The connector store: AES-GCM secrets, grants and an audit table. |
| `0005` | Drops the privilege and runbook tables. Privileges were superseded by connectors. |
| `0006` | Accounts: `users`, with id 1 as admin. Adds an `owner_id` to every user-data table, and composite foreign keys over `(parent_id, owner_id)`, so a row can never point at another user's row. |
| `0007` | Row-level security, plus the `muster_app` role. |
| `0008` | `mirror_tokens`. |
| `0009` | One chief per owner, and row-level security on `users`, `invites`, `api_tokens` and `audit_log`. |
| `0010` | `users.sessions_not_before`, a per-user session cutoff. |
| `0011` | `user_credentials` (bring-your-own Claude and OpenRouter keys). `cc_account_marks` becomes per owner. |
| `0012` | `flow_jobs` and `flow_runner_tokens`. |
| `0013` | `push_subscriptions` and `push_preferences`. |
| `0014` | `flow_requests`: an agent's request for a flow, which its owner approves. |
| `0015` | `plugins` and `plugin_messages`: the [plugin interface](plugins.md). A message's input cannot be changed after it is written. |
| `0016` | `plugin_reply_drafts` (a draft's body cannot be changed after it is written; the claim, lease and result rules) and `plugin_messages.no_reply`, which cannot be changed and refuses any reply draft for its message. |
| `0017` | `pins`: a user's pinned Agents-list entries, each naming an agent (deleted with it) or a mirrored window by `(host, session, tmux window id)`. Owned, under row-level security; the agent a pin names must be the pin's owner's. |
| `0018` | `recents`: a user's recently opened Agents-list entries, keyed as `pins` are, one row per entry (a visit moves its time), at most 50 per user (the oldest pruned). Owned, under row-level security. |
| `0019` | `send_queue`: the server-side send queue. Each row names a mirrored window (host, tmux session, window id) and carries the message, its state (`queued`, `sending`, `sent`, `failed`, `cancelled`) and the sign-in time of the session that queued it. At most one row per window is `sending`; its claim is a lease kept on the database's clock. Owned, under row-level security. Also `users.signed_out_at`: the latest "sign out everywhere", which the queue's delivery checks. |
| `0020` | `agent_focus`: each session's [focus](focus.md), one row per (owner, subject). A subject is an agent (by id, deleted with it) or a mirrored Claude Code session (by its Claude session id). Title, description, its source (`summarizer`, the only writer), the fingerprint of the transcript tail it was computed from, and the last refresh failure as a short non-secret reason, with its time. A generated `tsvector` over title (weight A) and description (B) with a GIN index serves `focus_search`. Owned, under row-level security. |
| `0021` | `session_routes`: one row per routed plugin message — its route id, the chief, the target session, the send-queue row that carried it, its state (`routed`, `answered`, `relayed`, `timed_out`, `fallback`, `failed`), the answer and the reply draft it became. At most one open route per message. Also `plugin_reply_drafts.route_id`, unique, so a route becomes at most one draft; `send_queue.route_id`, which marks a routed queue row (gated on its route at delivery); `session_routes.handback`, the hand-back an ended route still owes its chief (cleared by the sweep that delivers it); and `plugin_messages.sender_verified`, the plugin's immutable claim that it authenticated the sender. Owned, under row-level security. |
| `0022` | `agent_focus_history`: append-only, one row each time a session's focus title or description changes (title, description, when), written in the focus upsert's transaction. It has no foreign key to `agent_focus`: a session's history outlives its focus row, and is deleted after 30 days by the hourly sweep (a subject's newest row is kept while its focus row exists) or with its agent (`agent_id`, `ON DELETE CASCADE`). Existing focus rows seed one history row each. Owned, under row-level security. |
| `0025` | `attention_asks`: one row per question an agent (`agent_id`, deleted with it) or a mirrored Claude Code session (`mirror_host` + its Claude session id) put to its owner — the question, the options it offered, its state (`open`, `answered`, `cancelled`, `expired`), the answer (only the operator answers; see `0034` for where), when it expires. Each move out of `open` is one conditional update, so an answer and a cancel cannot both land. Owned, under row-level security. |
| `0026` | `attention_asks` gains the state `answered_in_session`: the operator wrote to the asker directly (a message into its mirrored session, or to the agent's chat) after it asked; the message, capped, is the answer, and `answered_by` is still `operator`. `answer_queue_id`: the send-queue row whose (queued) message answered it, for that row's "already answered" note (no foreign key: a display link). |
| `0031` | `attention_asks` gains the answer's DELIVERY to its asker: `delivery` (`queued` → `delivering` → `delivered` \| `unconfirmed`; `waited` when the asker read it with `attention_wait`; `pull` for a mirrored session; NULL when there is nothing to deliver, including every answer recorded before 0031 — no backfill), its lease (`delivery_claimed_by`, `delivery_lease_until`, set exactly while delivering), `delivery_detail` (why it waits or failed), `delivery_attempts`, `delivered_at` and `delivered_session_id` (a display link, no foreign key). Each move is one conditional update ([attention.md](attention.md#delivery)). |
| `0032` | `attention_asks.task_id`: the task an ask is about, written only by muster's own task path (`task_route_attention`, a mention's route to `/attention`), never from an asker's text. A plain foreign key to `notes` (`ON DELETE SET NULL`), its owner checked by a trigger (the ask's owner must own the task). Backfilled for asks the chief routed, matched by their `task.chief_routed` audit row. `agent_dispatch` accepts `instructions` only as the owner's answer to such an ask. Must apply after `0031`. |
| `0033` | `connector_grants.source` (`stored` \| `app`, default `stored`): which credential an approval was about — a stored connector row, or the [GitHub App](github-app.md). A grant whose source no longer matches what its connector is backed by (the App configured over a stored `github` token, or removed from under one) is put back to `pending` and must be approved again. Must apply after `0032`. |
| `0034` | `attention_asks` records where the operator gave an answer that did not come from `/attention`: `answered_via` (`mcp` for [`attention_answer`](attention.md#the-agent-tools), NULL for the view, an answer in the session and every answer recorded before 0034 — no backfill), `answered_via_host` and `answered_via_session` (the mirrored session it came from). `answered_by` stays `operator`. Its CHECK makes provenance all-or-nothing, only on an `answered` ask, with the mirror wire's host and session shapes, and never from the host a mirrored asker is on (`mirror_host = answered_via_host` is refused, whichever session answers). `agent_dispatch` accepts an answer with `answered_via` set as instructions like any other (operator decision), and its audit row then records `instructions_via` / `instructions_from`. Must apply after `0033`. Rollback: an image from before 0034 runs unchanged over it (it never writes the columns); to remove them, drop the constraint and the three columns and delete `schema_migrations` row 34 (the SQL is in the migration's header). |
| `0035` | `connector_grants` records where the operator decided a request that was not decided on the Connectors tab: `decided_via` (`mcp` for [`connector_request_decide`](connectors.md#deciding-a-request-from-your-own-session), NULL for the tab, a pending or revoked grant and every decision recorded before 0035 — no backfill), `decided_via_host` and `decided_via_session` (the mirrored session it came from). `decided_by` stays `operator`. Its CHECK makes provenance all-or-nothing, only on an `approved` or `denied` grant, with the mirror wire's host and session shapes; re-opening and revoking a grant clear it in the same statement. Must apply after `0034`. During a rolling deploy, an old pod's revoke or re-open of a grant a new pod just decided over MCP is refused by the CHECK (a 500 until that pod is replaced; measured at the SQL level, not on a live deploy). Rollback, in order, with the exact SQL in the migration's header (`[rollback-sql]`, `[restore-sql]`; `TestMigration0035RollbackAndRestore` runs both as written): (1) **before** rolling the image back, drop the CHECK **and** set all three columns to NULL — an older image never clears them, so a grant it re-opens and approves on the tab would otherwise keep a stale "via MCP" source; (2) roll the image back — `schema_migrations` keeps row 35, so a roll-forward does not re-apply 0035; (3) at roll-forward, before the new image takes traffic, set the columns to NULL again and re-add the CHECK. To remove the columns instead, after (1) and the image rollback drop them and delete `schema_migrations` row 35. |
| `0036` | The four stored session keys — `agent_focus.subject_key`, `agent_focus_history.subject_key`, `session_routes.target_key`, `attention_asks.mirror_session` — admit a Hermes conversation's key (narrowed again by `0085`, when Hermes support was removed) as well as a Claude Code id: `hermes:` and an id of 1–128 characters (Hermes ids are `local-<64 hex>`, 70). A bare id stays at 64, so every key stored before is still valid and a Hermes key is never read as a Claude one. The expression is `mirror.SessionKeyPattern`; a test pins that the migration spells it. `attention_asks.answered_via_session` (0034) and `connector_grants.decided_via_session` (0035) are deliberately left at 64: each names an MCP caller. Must apply after `0035`. Rollback: an image from before 0036 runs unchanged over it (it writes only Claude ids, which still match); to restore the old CHECKs, delete any `hermes:` rows, re-add each constraint with `'^[0-9A-Za-z][0-9A-Za-z_-]{0,63}$'`, and delete `schema_migrations` row 36. |
| `0037` | `jobs`: one row per machine job ([jobs.md](jobs.md)) — the agent (`agent_id`, set NULL when the agent is deleted, and `agent_name`, kept), the prompt, `repo`, `sha` (a full 40-hex commit id, or empty), `result_path`, `timeout_s`, `idempotency_key` (unique per owner), `requested_by` (the service caller's `X-Muster-Actor`), `status` (`queued` → `running` → `succeeded` \| `failed` \| `timed_out`), `result` (verbatim, at most 1 MiB, only on `succeeded`), `reason` (only on `failed` / `timed_out`) and `error` (on every `failed` / `timed_out` row, and on a `succeeded` one only as a note: a result file or a job worktree that was left in place), `cc_account`, `session_id` (the chat session the turn ran in; a display link, no foreign key) and the timestamps. Each move is one conditional update; a `queued` or `running` row past its own deadline is failed with reason `interrupted` by the reaper (`jobs.Store.ReapOverdue`, at boot and every minute), never one still inside it. Owned, under row-level security. Rollback: an image from before 0037 never reads the table; to remove it, `DROP TABLE public.jobs` and delete `schema_migrations` row 37. |
| `0038` | `agents_kind_check` admits `hermes` beside `gateway` and `claude-code` (the hermes kind, since removed; see `0047`). Nothing else changes: a hermes row names no Claude account (0003's `agents_cc_account_matches_kind`), and its kind is fixed for life (0003's trigger). Must apply after `0037`. 🔴 **Forward-only once a `hermes` row exists:** re-adding the old CHECK fails on that row. Before any hermes agent is dispatched, rollback is: re-add the CHECK without `hermes` and delete `schema_migrations` row 38; after, every `hermes` agent must be deleted first. |
| `0039` | Paired phones ([design/android.md](design/android.md#the-device-credential)): `devices`, one row per paired phone — the sha256 of its `mdv_` credential, its step-up public key with the key's type and Keystore level (all three NULL for a phone that paired read-only), `paired_signin_at` (the pairing session's sign-in time, compared with `users.sessions_not_before` and `users.signed_out_at` on every request) and `last_seen_at`; `device_pairing_codes`, single-use codes stored as a hash with a 60 s expiry. `push_subscriptions` gains `kind` (`browser` \| `android`) and `device_id`: an `android` subscription always names its device (through `(device_id, owner_id)`, so never another user's), a `browser` one never does, a device holds at most one, and deleting the device deletes it. A revoked device is deleted, never flagged. Both new tables are owned, under row-level security, and re-applied by `db.RLSOn`. Must apply after `0038`. Rollback: to remove it, delete the `android` rows of `push_subscriptions`, drop `push_subscriptions_kind_check`, `push_subscriptions_device_owner_fkey`, `idx_push_subscriptions_device` and the two columns, drop `device_pairing_codes` and `devices`, and delete `schema_migrations` row 39. |
| `0040` | `send_queue` gains a queued message's EDIT HOLD and its last saved edit: `held_until` and `hold_token` (an edit's hold, a lease on the database's clock of 10 minutes; the dispatcher's claim skips a row whose hold is live, in the same conditional update), `hold_lapsed_at` (a hold that ran out unsaved: the dispatcher's every pass, and a claim, take a lapsed hold off its row and record it here, so a row carries `held_until`/`hold_token` only while its hold is LIVE), `edited_at` and `edit_stepup_at` (when an edit was saved, and the sign-in of the request that saved it, which the delivery checks as it checks `stepup_at`). Its CHECKs keep a hold and its token together, only on a `queued` row (`send_queue_hold_check`), and an edit's time and sign-in together. Must apply after `0039`. 🔴 **An older image cannot write a row that has a hold.** Its claim, Cancel, the cancel on a disable or sign-out everywhere (`CancelOwner`) and its 7-day expiry each move a row out of `queued` without clearing the hold, and `send_queue_hold_check` refuses each one: on a held row the claim fails (so neither image sends it), a Cancel answers 500, and an expiry pass that meets one fails as a whole (measured in SQL). Because the new image takes a hold off its row within a pass of it running out, an older pod meets only holds that are being edited right now (at most 10 minutes and a pass). **Rollback, in this order:** (1) stop the holds being made — scale the new image down, or drop the CHECK first (`ALTER TABLE send_queue DROP CONSTRAINT send_queue_hold_check`), so that nothing an older pod does can trip it; (2) clear every hold (`UPDATE send_queue SET held_until = NULL, hold_token = NULL WHERE held_until IS NOT NULL`); (3) roll the image back. An older image then runs over the columns, except that it does not check `edit_stepup_at` on an edited message. A roll-forward re-adds the CHECK only if it was dropped: `ALTER TABLE send_queue ADD CONSTRAINT send_queue_hold_check CHECK (…)` exactly as in the migration, after step (2). To remove the columns instead, drop both CHECKs and the five columns and delete `schema_migrations` row 40. |
| `0041` | Worker pools for machine jobs ([jobs.md](jobs.md#worker-pools)): `agents.worker_pool` (default `''`), the pool a `claude-code` agent serves — its CHECK refuses a pool on any other kind, and a name outside `^[a-z0-9][a-z0-9-]{0,62}$` (`agents.ValidWorkerPool`); set at creation, never written after — `jobs.pr`, the pull request a `sha` job's commit is on (`0` without a `sha`; `CHECK pr >= 0`, not paired with `sha` so rows from before 0041 stay valid), and `jobs.worker_pool`, the pool a job was submitted to (`''` for a job that named its agent; the worker chosen is `agent_id` / `agent_name` as before). No pool table: a pool exists while an agent carries its name. Rollback: an image from before 0038 never reads either column; to remove them, drop both columns and delete `schema_migrations` row 41. |
| `0042` | `agents.gateway_secret` (default `''`): a `claude-code` agent's own random turn credential ([configuration.md](configuration.md#ccd-inside-the-claude-code-agent-image)) — the bearer muster sends to ccd's `/v1/responses`, shipped to the pod as `MUSTER_GATEWAY_BEARER`, and NOT derivable from `hooks_token` (which the agent's session holds). Minted by the provisioner on the agent's next apply (Stop then Start); `''` = none yet (every other kind, and a claude-code row whose pod predates it: it keeps the hooks-sha256 bearer). Rollback: an image from before 0042 never reads the column, but a pod applied by 0042 holds only the minted secret, so every migrated claude-code agent answers 401 until it is Stopped and Started under the older image; rolling forward again, a pod the older image applied in between is 401 until another Stop/Start. To remove the column, drop it and delete `schema_migrations` row 42. |
| `0043` | `connector_standing_grants`: the owner's [shared approvals](connectors.md#shared-approvals) — one row per approval shared with all of the owner's agents: `connector_name`, `source` (`stored` \| `app`), `repo` (for `app`, the agent's repository, lowercased, never empty; for `stored`, always `''`), `origin_grant_id` (the grant whose approval created it; a display link, no foreign key), `created_at` and `revoked_at` (a revoked row is kept). At most one live row per `(owner_id, connector_name, source, repo)`. `connector_grants.standing_grant_id` names the standing grant that approved a grant automatically, through `(standing_grant_id, owner_id)`, so never another owner's; 0035's `connector_grants_decided_via_check` is replaced by one that also admits `decided_via = 'standing'`, only on an `approved` grant that names its standing grant and no mirror host or session (and requires `standing_grant_id` NULL otherwise). Owned, under row-level security, and re-applied by `db.RLSOn`. Must apply after `0042`. Rollback: an older image's revoke and re-open do not clear `standing_grant_id`, so before rolling back clear the provenance (`UPDATE connector_grants SET decided_via = NULL, standing_grant_id = NULL WHERE decided_via = 'standing' OR standing_grant_id IS NOT NULL`) and put back 0035's CHECK (the SQL is in the migration's header); the older image then asks per agent again. To remove the schema too, drop the foreign key, the column and the table, and delete `schema_migrations` row 43. |
| `0045` | `agents.stopped_at`: when the row last moved into `stopped`, stamped by the trigger `agents_stopped_at` on every insert or status write that enters `stopped`, whatever the writer; kept when the row leaves `stopped` (the [stopped-agent reaper](provisioner.md#reaping-stopped-agents) reads it with the status). `agents.first_started_at`: the first time the row was written `provisioning` or `running` by an update (the same trigger; never moved by a later status write), so an agent saved for later and never started has none and is never reaped; backfilled with the migration's time only for rows that are `running` or have kickoff evidence (`kicked_off`, `kickoff_pod`, `kickoff_attempts`), every other row left without one. `agents.reap_claimed_at`: the reaper's claim, set by one conditional update before a teardown and cleared by the trigger on the next entry into `stopped`. Backfill: rows already `stopped` get the migration's own time, not their `updated_at`, so nothing is reaped until a full window after 0045. Rollback: an image from before 0045 never reads the columns; to remove them, drop the trigger, its function `muster_agent_stopped_at()` and the three columns, and delete `schema_migrations` row 45. |
| `0046` | `flow_jobs.ttl_paused` (INTERVAL, default `0`): the ttl credit a queued flow job earns while blocked behind a running job on the same owner/host/instance ([browser-flows.md](browser-flows.md)). Its effective deadline is `expires_at + ttl_paused`; `expires_at` stays the immutable as-enqueued value, and `ttl_paused` is not in the input-immutability trigger. The store adds credit when the blocker leaves `running` (Report or lease sweep), at most `MaxTTLPause` (90 min) per blocker. While a job is blocked, its deadline also counts the current blocker's hold, up to 90 min, so it expires only once that blocker has run past the ceiling. Rollback: an image from before 0046 ignores the column, so its first sweep expires every queued job past its RECORDED `expires_at`, including every job that is merely blocked behind a long dispatch. Expect those to show `expired` and re-enqueue them. Rolling forward again is safe: the credit is recomputed from the next blocker that finishes. To remove the column, drop it and delete `schema_migrations` row 46. |
| `0047` | `agents_kind_check` narrows back to `gateway` and `claude-code`: the `hermes` kind is removed (the last tree that had it is `d46b22e1`). 🔴 **It refuses to run while any `hermes` agent row exists** — its own check raises with the row count and the remedy (destroy those agents with a build that still has the kind), in the migration's transaction, so nothing changes. `agents.Kinds` is pinned to this list by `TestKindsMatchTheMigrationsCheck`. Rollback: re-add 0038's CHECK and delete `schema_migrations` row 47 — an older build then runs as before, with no hermes rows. |
| `0048` | `suggest_preferences`: one row per user who turned [suggested replies](suggested-replies.md) off (or back on): `owner_id` (the key), `disabled`, `updated_at`. No row means on. It holds no suggestion text. Owned, under row-level security, and re-applied by `db.RLSOn`. Rollback: an older image ignores the table; to remove it, drop it and delete `schema_migrations` row 48. |
| `0049` | `suggest_usage`: one row per user who has been shown a [suggested replies](suggested-replies.md) set: `owner_id` (the key), `shown`, `filled`, `sent`, `edit_sum` (counts, each `>= 0`), `paused` (the auto-pause), `updated_at`. Numbers only: no column holds a suggestion, a session or any conversation content. Owned, under forced row-level security, and re-applied by `db.RLSOn`. Rollback: an older image ignores the table (and keeps its tallies in memory again); to remove it, drop it and delete `schema_migrations` row 49. |
| `0050` | `attention_asks` gains `to_chief` (a mirrored session's question to the owner's chief, [`chief_ask`](attention.md#asking-the-chief): the chief may answer it and the Attention queue does not list it), `route_id` (the routed message a question is about) and `chief_turn_at` (when its turn to the chief started; NULL is due for the attention sweep's retry); `answered_by` admits `chief`. Not re-applied by `db.RLSOn`. Rollback: in the file's header. |
| `0051` | `plugin_messages.settle_reason` and `attention_asks.plugin_message_id` (unique; a plain foreign key, `ON DELETE SET NULL`), with a `pre-existing` backfill: a plugin message the chief did not act on becomes one ask ([plugins](plugins.md#a-message-the-chief-does-not-act-on)). Must apply after `0050`. Rollback: in the file's header. |
| `0052` | A stored session key may name an **opencode** session, `opencode:<id>` (id 1-128 characters): the four session-key CHECKs (`agent_focus.subject_key`, `agent_focus_history.subject_key`, `session_routes.target_key`, `attention_asks.mirror_session`) are re-created with the wider pattern `mirror.SessionKeyPattern` spells. ## Row-level security

Every owned table has row-level security turned on (`ENABLE` + `FORCE`) with an
`owner_isolation` policy. A connection sees and writes only the rows whose
`owner_id` matches its `muster.uid` setting, unless `muster.scope = 'all'`.

On **every pool acquire**, `internal/db` sets both settings from the request's
principal. It also switches to the `muster_app` role, because a superuser login
bypasses row-level security. A context with no principal sees nothing and inserts
nothing. `psql`, `pg_dump` and backups connect as the login role and still see
every row.

🔴 **Restoring a backup into a fresh Postgres.** `muster_app` is a cluster role,
and `pg_dump` does not carry it. So the dump's `GRANT … TO muster_app` lines fail,
and `ON_ERROR_STOP` stops at the first one. You can avoid this either way:

- restore without `ON_ERROR_STOP`;
- or run `CREATE ROLE muster_app NOLOGIN` first.

Then boot: the migrator re-creates the role and its grants on every run
(`internal/db/approle.go`).

🔴 **Rolling the image back below `0007`.** An older image never sets
`muster.uid`, so every insert it makes fails. Before you change the image, turn
row-level security off **from the current binary**:

- run `/muster-migrate --rls-off` in the current pod;
- or apply `internal/db/rollback/rls_off.sql` with psql.

The older image's `/muster-migrate` does not know the flag. It says "nothing to
apply", exits 0, and leaves row-level security on. `--rls-off` and `--rls-on`
each print the state of every owned table, and fail if any table is wrong.

## Two properties worth knowing before you change it

- 🔴 **Every `id` is `GENERATED ALWAYS AS IDENTITY`.** `internal/db/migrate_test.go`
  asserts this for every identity column in the schema, not a list of named ones.
  Weakening a column to `BY DEFAULT` would go unnoticed for months: it changes
  nothing about how muster writes, and only matters when someone assumes a
  hand-written `INSERT` importer is fine. Existing rows are meant to arrive by
  `pg_dump --data-only`, whose `COPY` path is exempt from the restriction.
- ⚠ **Some columns deliberately have no foreign key**, such as
  `task_sessions.session_id` and `notes.source_session_id`. They name things in
  other systems, or they are audit rows that must outlive their subjects. Adding
  a foreign key to one of them is not a cleanup.
